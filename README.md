# HTTP 路由冲突实验室

基于 **Node.js + Express + 原生前端**（零前端构建）的交互式实验室：
按优先级维护一组 HTTP 路由规则，系统实时判定规则之间的**完全遮蔽**与**部分重叠**，
并为每个冲突生成两条规则**都能命中的最短示例路径**（段数相同并列时取字典序最小者）。
拖动行调整顺序后结果立即重算。还可一键**生成修复方案**：把规则按语言等价关系分组、
将“更具体规则必须位于严格覆盖它的规则之前”建模为约束图，给出确定性的建议顺序，
预览调整前后位置与残留遮蔽数后一次应用；当页面上存在路由行为契约时，有效的**命中型契约**
会被纳入同一张约束图（仅当目标规则覆盖契约整个路径空间时才建立“目标在前”约束），
预览同时给出每条契约修复前后状态，目标无法被重排满足（目标不全覆盖、无匹配契约空间已被
覆盖、或合并后成环）时不出具可应用方案，并逐条标出不可满足契约、最短见证请求与冲突约束。
支持规则集的 JSON 导入 / 导出。
另支持**请求行为回归预演**：逐行输入“方法 路径”的真实请求样例，按当前优先级计算
首条命中规则，并在修复方案预览中用同一批样例对比建议顺序前后的命中变化。
以及**版本差异审计**：导入一份基线路由表（旧版本规则），与当前规则表按首条命中语义
在自动机上做**全空间**对比，找出新增覆盖、丢失覆盖与命中迁移的请求空间，
为每类变化给出确定性的最短见证请求，点击见证可回填请求预演逐条复核。
还支持**路由行为契约**：每条契约由一个**具体请求方法**、一个沿用规则语法的**路径模式**
（静态段 / `:参数` / `*` 通配符）以及一个期望——**应由指定规则首条命中**或**应无匹配**
——组成；系统在契约覆盖的**整个请求空间**（而非有限样例）上验证当前优先级，
失败时返回**段数最少、同长度字典序最小**的具体反例及其实际首条命中，点击反例可回填
请求预演。规则或契约编辑后自动重算，契约保存至浏览器 localStorage。

## 一条命令启动

```bash
docker compose up --build
```

然后打开 <http://localhost:3000>。

> 不想用 Docker 时：`npm install && npm start`，同样访问 <http://localhost:3000>。

## 路径语法

| 段类型     | 示例               | 匹配范围                         |
| ---------- | ------------------ | -------------------------------- |
| 静态段     | `/users/profile`   | 字面匹配该段                     |
| 参数段     | `/users/:id`       | `:id` 匹配**一个非空**段         |
| 通配符段   | `/assets/*`        | `*` 匹配**零个或多个**任意段     |
| 根路径     | `/`                | 仅匹配空段序列                   |

- 规则在列表中的**自上而下顺序即匹配优先级**（与 Express 的注册顺序一致）。
- 请求方法可选择常见方法或 `ALL`；`ALL` 表示与任意方法比较。不同具体方法的规则互不冲突。
- `*` 必须独占一个路径段（如 `/assets/*`），段内混写（`/assets/*.css`）会报语法错误。

## 冲突类型

- **⛔ 完全遮蔽（shadow）**：高优先级规则能匹配的路径集合 ⊇ 低优先级规则，
  因此低优先级规则永远不会被执行。
  例：`GET /*` 位于 `GET /health` 之前。
- **⚠️ 部分重叠（partial）**：两条规则都不是对方的超集，但存在同时命中的路径。
  例：`GET /a/*` 与 `GET /*/b`，同时命中的最短路径为 `GET /a/b`。

每个冲突卡片展示双方规则、关系说明，以及最短示例请求（点击可复制）。
列表中对应规则行会高亮并标注“遮蔽 N 条 / 重叠 N 条”。

**最短示例的约定**：需要由参数或通配符自由取值的段统一使用最小段值 `a`；
在段数最少的前提下，按 UTF-16 字典序选择最小的路径，保证结果唯一确定。

## 生成修复方案（确定性重排）

点击结果区的 **🛠 生成修复方案**（存在遮蔽或被违反的有效契约时出现），系统会：

1. **按语言等价关系分组**：路径语言互相覆盖（`L(x) ⊇ L(y)` 且 `L(y) ⊇ L(x)`）、
   且方法兼容的规则合并为一个语言等价组（并查集，如重复规则、`GET /x` 与 `ALL /x`）；
2. **构建约束图**：对每条“i 的路径严格覆盖 j 的路径”的规则对，在组与组之间添加
   有向边 `j → i`，表示**更具体的规则必须排在严格覆盖它的规则之前**。严格覆盖是
   严格偏序，因此约束图必然无环；
3. **确定性拓扑排序**：Kahn 算法，并列时按组内最小的原始索引升序，组内保持原始
   相对顺序——相同输入永远得到相同建议顺序；
4. 输出每条规则**调整前 → 调整后**的位置；并按建议顺序重新跑一遍完整分析，
   给出**调整后仍不可避免的遮蔽数量**。

> **不会把无法修复的冲突伪装成已修复**：语言等价、方法又兼容的规则（互相覆盖）
> 在任何顺序下都存在遮蔽，它们所在的等价组会被明确标记为
> “不可通过排序消除”，并在预览中逐条列出应用后仍存在的遮蔽；这类冲突只能通过
> 合并、删除或改写路径解决。可经排序消除的遮蔽在重排后会降级为部分重叠（不再遮蔽，
> 但仍在冲突卡片中标注）。

预览面板展示：调整前/后遮蔽数、仍不可避免的遮蔽数、需移动规则数、完整建议顺序、
不可消除等价组与残留遮蔽清单。确认后点击**一次应用**即可整体重排；应用后沿用现有
实时分析自动重算，并照常保存到浏览器 localStorage。规则被增删、拖拽、导入或重置时，
已打开的预览会自动关闭，避免索引过期。

### 修复方案 × 路由行为契约（命中型契约纳入约束图）

携带契约时，生成修复方案会把**有效的命中型契约（`-> #N`）**与上述严格覆盖约束
**合并到同一张约束图**：

1. **前置条件——目标必须覆盖契约整个路径空间**：只有当 `L(目标规则) ⊇ L(契约模式)`
   （且目标规则有效、方法兼容——契约为具体方法时，目标为该具体方法或 `ALL`）时，
   契约才可能经重排满足；
2. **建立“目标规则在前”约束**：前提成立时，为目标规则与**每一条**同方法
   （契约方法相同或规则为 `ALL`）且**在契约覆盖空间有交集**的竞争规则建立有向边
   “目标组 → 竞争组”（边描述带确定性的最短交集请求）；
3. **合并与确定性顺序**：契约边并入严格覆盖边构成的无环图后，仍用 Kahn 做确定性
   拓扑排序（并列规则不变），输出同一套确定性建议顺序；
4. **不可通过重排满足时不出具方案**。出现以下任一情况，预览会标红并逐条列出
   **不可满足的契约、最短见证请求与冲突约束**，且不提供“一次应用”：
   - `target-not-cover`：目标规则不覆盖契约整个路径空间（见证 = 契约接受而目标不接受的
     最短请求，如目标为 `/api/users/:id`、契约为 `/api/users/*` 时见证 `/api/users`）；
   - `target-incompatible`：目标规则方法与契约方法不兼容；
   - `covered`：**无匹配（none）契约**的路径空间已被任意规则覆盖——重排不改变可命中
     的请求集合，最短命中即见证；
   - `equivalent-group`：竞争规则与目标规则路径语言等价、方法兼容且原本就在目标之前，
     等价组内任何顺序都有遮蔽；
   - `cycle`：合并后的约束图成环（严格覆盖边无环，环必由契约边引入）；见证为该契约
     最短交集请求，冲突约束按 BFS 给出环上的完整边序列（覆盖边 + 闭合环的契约边）。
   - 因状态空间安全上限未能完成验证（`truncated`）的契约不影响逐对精确判定
     （覆盖/交集都是两个 DFA 间的精确判定），仍正常纳入约束图。

**修复前后契约状态预览**：可行时预览逐条给出契约在当前顺序与建议顺序下的全空间验证结果
（`pass` / `fail` / `truncated`）及汇总（成立/违反/未完成的前后计数）。

**应用后自动重映射**：一次应用只改变规则顺序、规则内容一一对应；命中型契约的目标按
**原规则**自动换算到新位置（0-based `ruleIndex = 新位置`），并随契约一起保存到
localStorage，应用后立刻按重映射目标重新全空间验证。无匹配契约无需重映射。

> 仅有契约违反、没有遮蔽时也会出现“生成修复方案”按钮（存在可经重排满足的契约时
> `needed` 为真）。不可行时按钮仍可打开诊断预览，但预览内没有任何可应用顺序。

## 请求行为回归预演

结果面板顶部的**请求回归预演**区支持逐行输入真实请求样例（每行格式：`方法 路径`）：

```
GET /api/users/123
POST /api/users
DELETE /assets/css/site.css
```

- 系统按**当前优先级**逐条计算**首条命中规则**，结果按输入顺序展示并标注原始行号；
  点击命中规则芯片可滚动定位并高亮对应规则行；
- 命中语义与冲突分析一致：`ALL` 规则可被任意方法命中，`*` 匹配零或多个段，
  `:param` 匹配一个非空段；不同具体方法的规则互不影响；
- 样例校验：方法必须是**具体方法**（`GET`/`POST`/…，不接受 `ALL`），路径必须是
  **具体路径**（不接受 `:参数` 与 `*`）；无效样例逐条标注错误原因，空白行自动忽略；
- 规则编辑、拖拽重排、导入或重置后，全部样例**自动重算**；样例文本保存到浏览器
  localStorage，刷新后保留；
- 打开 **🛠 生成修复方案** 预览时，同一批样例会按**建议顺序**再算一遍首条命中，
  逐条对比并标出：**命中改变**、**原本无匹配**、**调整后无匹配**的请求
  （重排不改变可匹配的请求集合，因此无匹配通常前后一致；命中规则可能因优先级
  变化而改变）。对比行中的规则同样可点击定位。

## 版本差异审计（基线对比）

页面底部的**版本差异审计**面板支持导入一份**基线路由表**（旧版本规则），与当前规则表
按**首条命中语义**做全空间对比——不是抽样检查：对每个具体方法，复用路径自动机构建
两侧全部规则的联合乘积自动机，遍历整个请求空间，找出：

- **🟢 新增覆盖**：当前版本可命中、基线无匹配的请求空间（按**当前规则**归组）；
- **🔴 丢失覆盖**：基线可命中、当前版本无匹配的请求空间（按**基线规则**归组）；
- **🟠 命中迁移**：两侧均可命中、但命中规则不同的请求空间
  （按**基线规则 → 当前规则**归组）。命中规则是否“相同”按规范化方法 + 路径判定，
  与规则在表中的位置无关——单纯重排不会产生伪差异。

每一类变化都给出**确定性的最短见证请求**：段数最少；并列时方法按
`GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS` 顺序、路径按 UTF-16 字典序最小；
自由段取值约定与冲突示例相同（固定 `a`；若 `a` 本身是某条规则的字面量，
则另选 `b`、`c`… 作为非字面量代表，保证仅经非字面量段可达的差异类也不漏检）。
点击见证请求即可**回填到请求预演**输入框，随预演立即按当前优先级复核首条命中。

操作：

- **导入基线 JSON**：从文件导入基线（格式同规则导出文件，兼容裸数组）；
- **快照当前为基线**：把当前规则表直接固定为基线，随后继续编辑即可实时审计改动影响；
- **清除基线**：退出对比。

规则编辑、拖拽重排、导入或重置后，差异结果**自动重算**；基线规则表可展开只读查看，
其中语法错误的条目会被标注并在对比中忽略。基线只保存在浏览器 localStorage，
不会持久化到服务器。

## 路由行为契约（全空间验证）

页面中的**路由行为契约**面板用于把“某块请求空间理应被哪条规则首条命中（或理应无匹配）”
固化为可重复验证的契约。每条契约由三部分组成：

- **具体请求方法**：`GET` / `POST` / `PUT` / `PATCH` / `DELETE` / `HEAD` / `OPTIONS`，
  不接受 `ALL`（契约逐具体方法成立；规则中的 `ALL` 规则仍会以契约方法参与命中）；
- **路径模式**：与路由规则**完全相同的语法**——静态段 `/users/profile`、
  参数段 `/users/:id`（匹配一个非空段）、通配符段 `/assets/*`（匹配零或多个段）；
- **期望**：
  - **应由 #N 首条命中**：该模式覆盖的每一个具体请求，按当前优先级都必须首条命中
    第 N 条规则（命中别的规则、或无匹配，都算违反）；
  - **应无匹配 (none)**：该模式覆盖的每一个具体请求都必须无任何规则命中。

**全空间验证，而非抽样**：后端把契约模式 DFA 与全部方法兼容的有效规则 DFA 做联合乘积，
沿契约模式仍然存活的方向枚举所有可达乘积状态——字母表取契约模式与规则中的全部字面量，
再加一个非字面量代表段值（固定取 `a`；若 `a` 本身是字面量则顺延取 `b`、`c`…），
它精确代表“任何非字面量段”的等价类，因此枚举是完备的：模式包含无限多具体请求时
也能给出确定结论。规则或契约被编辑、增删后随实时分析**自动重算**（同一套防抖机制）。

验证失败时给出**确定性的最短反例**：段数最少；并列时路径按 UTF-16 字典序最小
（自由段统一取 `a`），并附上该反例的**实际首条命中**规则（或“无匹配”）。
例如规则顺序为 `GET /api/*` 在 `GET /api/users/:id` 之前，契约
`GET /api/users/:id -> #2` 会失败，最短反例为 `GET /api/users/a`，实际命中
`#1 GET /api/*`；契约 `GET /api/users/* -> #2` 的最短反例则是更短的零段请求
`GET /api/users`（`*` 匹配零段）。

- 点击反例请求会**回填到请求行为回归预演**输入框（去重追加、立即重算），点击实际命中
  规则可滚动定位到规则行；
- **无效契约逐条提示且不参与验证**：方法非法（含 `ALL`）、路径模式语法错误、
  期望缺失或格式非法、目标规则序号超出当前规则表范围等，都会在该行逐条列出原因，
  并在汇总中单列“无效 N”，不影响其余契约的验证（规则被删除导致期望序号失效时同理）；
- 契约列表随规则编辑保存到浏览器 **localStorage**（键
  `route-conflict-lab.contracts.v1`），刷新后保留，不持久化到服务器；
- 若某契约的乘积状态数超过安全上限，该行如实标注“状态空间超限，未能完成全空间验证”，
  绝不会把未验证完的空间算作成立。

### 契约格式

页面表单直接编辑即可；通过 API（或将来的导入）可使用字符串行或对象：

```text
GET /api/users/:id -> #2
GET /admin/* -> none
```

- 字符串行格式：`方法 路径模式 -> #序号` 或 `方法 路径模式 -> none`
  （箭头也支持 `=>`；`none` 大小写不敏感，也接受中文“无匹配”）；
- 对象格式：`{ "method": "GET", "path": "/api/users/:id", "expect": "hit", "ruleIndex": 2 }`
  或 `{ "method": "GET", "path": "/admin/*", "expect": "none" }`，
  其中 `ruleIndex` 为 **0-based** 规则序号（字符串行的 `#N` 为 1-based）。

## JSON 导入 / 导出

导出文件格式（也兼容直接导入裸数组）：

```json
{
  "format": "route-conflict-lab/v1",
  "exportedAt": "2026-09-19T00:00:00.000Z",
  "rules": [
    { "method": "GET", "path": "/api/*" },
    { "method": "GET", "path": "/api/users/:id" }
  ]
}
```

规则在 `rules` 数组中的顺序即优先级。页面会自动把当前规则集保存到浏览器 localStorage。

## HTTP API

- `POST /api/analyze` — 请求体：

  ```json
  {
    "rules": [{ "method": "GET", "path": "/x/:id" }],
    "samples": ["GET /x/1", "DELETE /assets/a.css"],
    "baselineRules": [{ "method": "GET", "path": "/x/*" }],
    "contracts": [
      "GET /x/:id -> #1",
      "GET /admin/* -> none",
      { "method": "POST", "path": "/x", "expect": "none" }
    ]
  }
  ```

  `samples` 可选（缺省时响应不含相关字段）：每行一个“方法 路径”字符串，
  也兼容 `{ "method": "GET", "path": "/x/1" }` 对象；空白行被跳过，最多 1000 条。

  `contracts` 可选（缺省时响应不含 `contracts` 字段，最多 200 条）：路由行为契约数组，
  元素为字符串行（`方法 路径模式 -> #序号` 或 `方法 路径模式 -> none`，
  也接受 `=>` 箭头与中文“无匹配”，空白字符串被跳过）或对象
  `{ method, path, expect: 'hit', ruleIndex }`（`ruleIndex` 为 0-based）/
  `{ method, path, expect: 'none' }`。携带时响应额外包含**契约全空间验证**结果：
  - `contracts.total` / `validCount` / `invalid` / `pass` / `fail` / `truncated`：
    契约总数、有效数、无效数、成立数、违反数、因状态空间安全上限未完成验证的数量；
  - `contracts.results[]`：按输入顺序逐条返回
    `{ index, line, input, method, path, valid, errors, status, expected, counterexample }`；
    `status` 为 `pass` / `fail` / `truncated` / `invalid`（无效契约不参与验证）；
    `expected` 为 `{ kind: 'hit', rule }`（`rule` 为规则引用）或 `{ kind: 'none' }`；
    违反时 `counterexample` 为确定性的最短反例
    `{ method, path, text, actualHit }`，`actualHit` 为实际首条命中规则引用
    （`{ index, id, method, path }`）或 `null`（实际无匹配）。

  `baselineRules` 可选（缺省时响应不含 `diff` 字段）：基线路由表，与 `rules`
  同格式、同样最多 500 条。携带时响应额外包含**版本差异审计**结果：
  - `diff.identical` / `diff.truncated`：两版本首条命中行为是否完全一致 /
    请求空间状态数是否因安全上限被截断（截断时结果可能不完整，如实标记）；
  - `diff.summary`：`added` / `lost` / `migrated` / `total` 差异类计数；
  - `diff.classes[]`：每类 `{ kind, baseline, current, witness }`；
    `kind` 为 `added`（新增覆盖）/ `lost`（丢失覆盖）/ `migrated`（命中迁移）；
    `baseline` / `current` 为该类在两侧命中的规则引用 `{ index, id, method, path }`
    或 `null`（该侧无匹配）；`witness` 为该类确定性的最短见证请求
    `{ method, path, text }`；
  - `diff.baseline`：基线校验信息 `{ total, validCount, invalid[] }`，
    无效基线规则不参与命中。

  返回逐条规则的校验/冲突标注、冲突列表（含 `type`、`higher`、`lower`、`example`）与汇总计数，
  并额外包含 `fixPlan` 修复方案对象：
  - `needed` / `feasible`：是否存在遮蔽**或被违反的有效契约** / 合并契约约束后是否可排序
    （严格偏序下无契约时恒为 `true`；契约可使 `feasible` 为 `false`）；
  - `shadowBefore` / `shadowAfter` / `fixedCount` / `unavoidableShadow`：
    调整前遮蔽数、应用建议顺序后重新分析得到的遮蔽数、可消除数、不可通过排序消除数；
  - `partialBefore` / `partialAfter`：调整前后的部分重叠数（被修复的遮蔽会转为重叠）；
  - `order`：建议顺序，即原始索引（0-based）的一个排列；**不可行时为 `[]`**；
  - `moves`：实际发生移动的规则及 `from` / `to`（1-based 位置）；不可行时为 `[]`；
  - `constraints`：约束边数组，`kind: 'coverage'` 为严格覆盖边
    （含 `narrower` / `wider` / `reason`，与旧版字段一致），
    `kind: 'contract'` 为“目标在前”契约边（含 `contract`、`target`、`competitor`、
    `witness`、`line`、`reason`）；
  - `equivalenceGroups`：语言等价组（`size > 1`）及组内不可消除遮蔽数、
    `resolvableByOrder` 标记；`unavoidablePairs`：等价规则对清单；
  - `residualConflicts`：应用后仍存在的冲突（含应用后的新位置与示例）；
  - `contracts`（**仅当请求携带 `contracts` 时出现**）：契约纳入约束图的结果——
    - `total` / `passBefore` / `failBefore` / `truncatedBefore`：有效契约数及修复前
      全空间验证计数；
    - `passAfter` / `failAfter` / `truncatedAfter`：建议顺序下的计数（不可行时为 `null`）；
    - `feasible`：是否存在可应用的重排顺序（与顶层 `fixPlan.feasible` 一致）；
    - `unsatisfiable[]`：不可通过重排满足的契约，逐条给出
      `{ line, contract, reason, reasonText, witness, conflicts }`：
      `reason` 为 `target-not-cover` / `target-incompatible` / `covered` /
      `equivalent-group` / `cycle`；`witness` 为确定性最短见证请求
      `{ method, path, text, actualHit }`；`conflicts` 为冲突约束清单
      （`kind: 'coverage'` 边含 `narrower`/`wider`；`kind: 'contract'` 边含
      `target`/`competitor`/`detail`）；
    - `results[]`：逐条有效契约的 `{ line, contract, method, path, expect, target,
      before, after, unsatisfiable, reason, witness, conflicts }`，
      `before`/`after` 为 `pass` / `fail` / `truncated`（不可行时 `after` 为 `null`）。
    无效契约不出现在 `fixPlan.contracts` 中（其逐条错误仍见顶层 `contracts` 结果）。

  请求携带 `samples` 时，响应额外包含**请求行为回归预演**结果：
  - `samples`：按当前优先级的首条命中计算
    - `total` / `validCount` / `unmatched`：样例总数、有效数、有效但无匹配数；
    - `results[]`：按输入顺序逐条返回 `{ index, line, input, method, path, valid, errors, hit }`；
      `line` 为原始输入行号（1-based），`hit` 为首条命中规则
      `{ index, id, method, path }`，无匹配为 `null`；
  - `fixPlan.sampleReplay`（仅当存在有效样例时）：同一批样例 × 建议顺序的前后对比
    - `total` / `changed` / `unmatchedBefore` / `unmatchedAfter`：有效样例数、
      命中改变数、原本无匹配数、调整后无匹配数；
    - `results[]`：`{ index, line, input, before, after, afterPosition, changed,
      unmatchedBefore, unmatchedAfter }`；`before` / `after` 为命中规则引用或 `null`，
      `after.index` 为规则原始索引，`afterPosition` 为建议顺序中的 1-based 位置。

顶层还包含 `signature`：当前规则集（顺序 + 方法 + 路径）的内容签名，前端据此判断
预览中的方案是否已因编辑而过期（样例不参与签名）。
- `GET /api/health` — 健康检查。

返回仅为**新增字段**（`fixPlan` / `samples` / `diff` / `contracts` 均为可选附加），既有
`rules` / `conflicts` / `summary` 结构不变；不携带 `contracts` 的旧请求响应中既不含顶层
`contracts` 字段，也不含 `fixPlan.contracts`，且 `fixPlan.constraints` 中不会出现
`kind: 'contract'` 边、`feasible` 恒为仅由严格覆盖偏序决定的结果。JSON 导入/导出仍使用
`route-conflict-lab/v1` 格式（裸数组同样兼容），修复方案、请求预演、版本差异审计与
契约验证均由后端即时重算，不需要持久化，因此导入导出格式完全向后兼容。

## 实现说明

分析核心位于 `lib/analyzer.js`（纯函数，无依赖）：每个路径模式被建模为带 ε 边的 NFA
（`*` 为“ε 跳过 + 任意段自环”），通过子集构造得到 DFA。

- 遮蔽判定：在两个模式的乘积 DFA 上搜索“B 接受而 A 不接受”的可达状态；
- 交集示例：在乘积 DFA 上按段数做 BFS，同层边按段值字典序处理，首个到达的共同接受状态
  即为“段数最少、并列字典序最小”的示例路径；
- 修复方案：对所有方法兼容的有效规则对计算双向覆盖关系，并查集聚成语言等价组，
  严格覆盖关系收缩为组间约束图后做确定性拓扑排序，再按新顺序重新分析得出残留遮蔽数；
  携带契约时，把有效命中型契约纳入同一约束图：先用 `covers(目标, 契约模式)` 精确判定
  目标是否覆盖契约全空间（不覆盖即给出“契约接受而目标不接受”的最短见证），覆盖时对所有
  方法兼容且与契约空间有交集（`shortestIntersectionWord` 非空）的规则加“目标组 → 竞争组”
  边；无匹配契约检查空间是否已被任意规则覆盖。Tarjan 强连通分量判定合并图是否成环，
  成环时用确定性 BFS 给出“竞争组 → 目标组”的最短闭合路径与该契约最短交集见证，
  逐条输出不可满足契约、见证与冲突约束且不输出可应用顺序；可行时按建议顺序重编译规则表、
  重映射契约期望序号后重跑全部契约验证，输出修复前后状态；
- 请求回归预演：样例的具体段序列在每条规则的 DFA 上逐段转移判定接受，按规则顺序取
  首条命中；修复方案用同一批样例在建议顺序的规则序列上重算，逐条对比命中变化；
- 版本差异审计：对每个具体方法，将两侧全部方法兼容的有效规则的 DFA 做联合乘积，
  按（段数、字典序）BFS 遍历全部可达乘积状态；状态标签为两侧各自的首条命中规则
  （按规范化方法 + 路径判定异同，与规则位置无关）。字母表取两侧全部字面量加一个
  非字面量代表值（若 `a` 本身是字面量则另选 `b`…），精确覆盖段值商集，因此是
  完备枚举而非有限抽样；每个标签不同的等价类记录最短见证（段数最少，方法按
  METHODS 顺序、路径按字典序打破并列）。状态数超过安全上限时停止展开并如实
  标记 `truncated`；
- 路由行为契约：逐条校验方法/路径模式/期望（无效契约仅提示、不参与验证），
  对每条有效契约把契约模式 DFA 与全部方法兼容的有效规则 DFA 做联合乘积，
  只沿契约模式仍然存活的转移展开（恰好限定在 L(契约模式) 覆盖的请求空间内），
  在每个契约模式接受的状态读取首条命中规则；字母表同样为全部字面量 + 一个
  非字面量代表值，故对无限请求空间也是完备判定。按（段数、字典序）BFS 遇到的
  首个违例状态即确定性最短反例（携带实际首条命中）；状态数超过安全上限时标记
  `truncated`，不把未验证完的空间算作成立。
